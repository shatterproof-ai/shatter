Shatter: automatic exploratory testing via concolic execution

Usage: shatter [OPTIONS] <COMMAND>

Commands:
  explore         Explore functions by analyzing their branches and generating test inputs
  analyze         Analyze Stage 1 (Observe) output: produce equivalence classes, behavior map, coverage metrics, and optional behavioral specification. No frontend or solver required — pure offline computation on serialized observation data
  observe         Run the observation stage: execute a function with generated inputs and write ObserveStageOutput JSON to a file or stdout. Use `shatter analyze` to process the output offline, or `shatter specify` to build a behavioral spec
  solve           Solve uncovered branches: read Stage 1 observation output and use Z3 constraint solver to find inputs that trigger uncovered branch directions. No frontend needed — pure offline computation on serialized observation data
  specify         Build a FunctionSpec from an observation file produced by `shatter observe`
  scan            Scan a directory for source files, analyze and explore all functions in dependency order, using behavior maps as mocks
  properties      Discover and export behavioral properties and invariants as a YAML spec
  run             Discover, analyze, and explore an entire repository in one shot
  diff            Compare current behaviors against a previous snapshot to detect regressions
  spec-diff       Compare two function specifications and report behavioral changes
  compare         Compare two function implementations across languages by input/output behavior
  build-frontend  Build a custom frontend binary with user-provided native generators
  discover-deps   Discover external network dependencies using strace (Linux-only diagnostic)
  stale           Check which functions in a source file are stale relative to a spec file
  revalidate      Re-execute cached behaviors to detect regressions or drift
  test            Run tests with impact analysis: only execute tests affected by changed files
  init            Initialize a repository for persistent Shatter project state
  telemetry       Manage anonymous usage telemetry
  cache           Manage the on-disk shatter cache
  workspace       Manage the Go frontend artifact workspace
  nondeterminism  Review and classify suspected-nondeterministic fields
  bench           Run benchmarks against a manifest of canonical scenarios
  list-targets    List source files that would be selected for a scan, with details about excluded, unsupported, and out-of-policy candidates
  doctor          Diagnose the local Shatter install
  help            Print this message or the help of the given subcommand(s)

Options:
      --log-level <LOG_LEVEL>
          Log verbosity level: error, warn, info (default), debug, trace
          
          [default: info]

  -v, --verbose...
          Increase verbosity (-v = debug, -vv = trace)

  -q, --quiet
          Decrease verbosity to warnings and errors only

      --timing <TIMING>
          Timing output mode
          
          [default: off]
          [possible values: off, summary, detailed]

      --timing-format <TIMING_FORMAT>
          Format for timing output. `json` and `both` are intended for persisted artifacts
          
          [default: text]
          [possible values: text, json, both]

      --timing-output <PATH>
          Write one timing artifact JSON file to this path

      --timing-output-dir <DIR>
          Write timing artifact JSON files into this directory

      --project-dir <DIR>
          Override auto-detected project root directory

      --allow-host-writes
          Permit executing target functions on the host without an OS sandbox.
          
          By default (str-gg9v) Shatter refuses to execute target functions when no sandbox backend is configured, because a target can create, modify, or delete files by relative path in the invoking repository. Pass this flag (or set `SHATTER_ALLOW_HOST_WRITES=1`) to opt in. Even with the opt-in, targets still run in a throwaway working directory so relative-path writes do not land in the repo. Configuring `SHATTER_SANDBOX_BACKEND=docker|bwrap` is the safer alternative and does not require this flag.

      --set <KEY=VALUE>
          Override config values using dotted-path key=value pairs (repeatable).
          
          Example: `--set defaults.max_iterations=200 --set defaults.exploration.adaptive=false`
          
          Keys follow the `.shatter/config.yaml` YAML structure. Values are parsed as YAML scalars (integers, floats, booleans, strings). Precedence: above any `.shatter/config.yaml` file but below dedicated flags like `--max-iterations`.

      --color <WHEN>
          When to use terminal colors: always, auto (default), or never. Respects the NO_COLOR environment variable (auto treats it as never)
          
          [default: auto]
          [possible values: always, auto, never]

      --render <MODE>
          Terminal rendering mode: md (default, rendered via termimad) or plain (legacy ANSI)

          Possible values:
          - md:    Markdown rendered via termimad (default). Use `--color never` for raw Markdown
          - plain: Legacy plain ANSI text output (deprecated)
          
          [default: md]

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version
